## Главный вопрос

MoyaStudia должна постепенно позволить пользователю управлять YouTube-контентом без постоянного использования YouTube Studio.

Нужно определить правильную границу:

**YouTube = внешний source of truth для опубликованного контента**

**MoyaStudia = рабочее пространство пользователя для подготовки и управления контентом**

Не надо пока реализовывать это. Нужно определить архитектуру.

## Обязательно разобрать

### 1. Video data model

Раздели существующие поля на:

- YouTube snapshot;
- MoyaStudia working fields;
- поля, которые должны быть вычисляемыми;
- поля, которые нельзя редактировать локально;
- поля, которые в будущем будут синхронизироваться обратно в YouTube.

Особенно рассмотри:

- title;
- description;
- tags;
- visibility;
- publish date;
- thumbnail;
- category;
- language;
- playlists;
- captions;
- duration;
- statistics;
- YouTube IDs/status;
- будущие scheduling/publishing fields.

Не придумывай лишние поля без необходимости.

### 2. Snapshot vs working copy

Определи, нужна ли отдельная модель/таблица для working state или достаточно расширить `Video`.

Рассмотри варианты и выбери один.

Объясни:

- почему;
- какие проблемы решает;
- как избежать потери YouTube snapshot;
- как обнаруживать изменения на YouTube;
- как определить `dirty`;
- как хранить draft;
- как впоследствии делать push изменений обратно в YouTube.

### 3. Ownership

Проверь, как новые working records должны быть связаны:

`User → GoogleConnection → Channel → Video → Working data`

или иначе.

Новые данные не должны нарушать существующую owner isolation.

### 4. Sync model

Определи поведение:

YouTube → MoyaStudia

MoyaStudia → YouTube

и что происходит при конфликте:

- пользователь изменил видео в MoyaStudia;
- видео одновременно изменилось в YouTube;
- выполнен новый catalog sync.

Не реализовывать conflict resolution сейчас, только определить правильную модель.

### 5. API

Спроектируй минимальный будущий API для Stage 4.

Например:

- получить video;
- изменить working fields;
- сохранить draft;
- определить dirty state;
- позже push changes.

Не создавать endpoints сейчас.

Отдельно укажи, какие endpoints нужны **сразу для первого Stage 4 increment**, а какие можно отложить.

### 6. Frontend

Посмотри текущий Studio и предложи минимальный первый UI increment.

Нужно определить:

- что пользователь увидит при выборе видео;
- где редактировать title/description/tags;
- как показывать `saved / modified / synced`;
- как отличать YouTube snapshot от локальных изменений;
- где разместить будущую кнопку Publish/Sync to YouTube.

Пока только архитектура и UI plan.

### 7. Playlists

Учти уже исправленный channel-scoped playlist behavior.

Определи:

- playlist membership хранить локально или получать live;
- как связать video ↔ playlist;
- что нужно для будущего добавления/удаления видео из playlist;
- что относится к Stage 4, а что позже.

### 8. Минимальный первый increment

После анализа предложи **самый маленький полезный Stage 4 increment**, который:

- не ломает текущий read-only catalog;
- даёт пользователю реальную новую возможность;
- не требует сразу полной YouTube write-back системы;
- создаёт правильный фундамент для следующих этапов.

## Важное ограничение

Не надо превращать Stage 4 сразу в полноценный YouTube Studio clone.

Нужна последовательная архитектура:

1. read-only catalog уже есть;
2. теперь добавить рабочее состояние;
3. затем редактирование;
4. затем безопасный write-back в YouTube;
5. затем более сложные функции.
