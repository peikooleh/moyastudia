# MoyaStudia — Stage 3
## Product usability refinement and first practical Studio workflow

Работай в существующем репозитории MoyaStudia.


Перед началом работы:
1. Прочитай AGENTS.md и актуальный STATUS.md.
2. Сверь текущий пункт этого промпта с фактическим состоянием репозитория.
3. Определи, какие пункты уже выполнены, а какие ещё нет.
4. Не повторяй уже выполненную работу.
5. Продолжай с первого действительно невыполненного пункта.
## 0. Главный принцип Stage 3

Stage 3 НЕ является глобальным редизайном приложения.

Текущий интерфейс в целом выглядит нормально и его базовая структура пользователя устраивает.

Задача Stage 3:

> аккуратно довести уже существующий интерфейс до состояния, в котором MoyaStudia можно минимально использовать как рабочий инструмент управления YouTube-контентом.

Не переизобретай приложение.

Сохраняй:
- существующий визуальный стиль;
- существующую систему компонентов;
- существующую общую навигацию;
- существующий layout там, где он уже удобен;
- существующую модель `Video: список слева + карточка справа`;
- уже работающие UX-решения.

Меняй только то, что действительно требует улучшения.

### Критически важно

Не делать глобальный UI/UX redesign только ради улучшения дизайна.

Не менять рабочие элементы без конкретной причины.

Работать по принципу:

> конкретная проблема → минимальное изменение → проверка → следующая проблема.

Если для реализации какого-либо пункта есть несколько вариантов, сначала проанализируй существующую архитектуру и выбери минимальный и наиболее естественный для текущего приложения вариант.

Не добавляй новые функции просто потому, что они потенциально могут пригодиться в будущем.

# 1. Сначала изучить проект

Перед изменениями:

1. Прочитать актуальный `STATUS.md`.
2. Прочитать `AGENTS.md` и все актуальные инструкции проекта.
3. Проверить `git status`.
4. Изучить текущий Studio UI.
5. Изучить существующие API и модели данных, связанные с:
   - videos;
   - playlists;
   - channels;
   - Google connections;
   - catalog;
   - video metadata.
6. Изучить текущие тесты.
7. Определить, какие элементы уже являются рабочими, а какие пока являются только отображением данных.

До начала изменений не переписывать архитектуру.

Сначала составить краткий внутренний план Stage 3 на основании реального состояния репозитория.

# 2. Video workspace — сохранить существующую модель

Текущая модель:

```text
слева                     справа

список видео              карточка выбранного видео
```

пользователю понятна и удобна.

Её сохраняем.

Не заменять её на:
- модальные окна;
- отдельные страницы каждого видео;
- новую сложную навигацию;
- другой глобальный layout.

Нужно улучшить именно существующую карточку видео.

# 3. Title / Description / Tags

Сейчас основные текстовые поля визуально выглядят красиво, но слишком малы относительно реальных объёмов данных YouTube.

Проблема:

- Title занимает мало места;
- Description показывает только несколько строк;
- Tags также визуально слишком ограничены;
- значительная часть содержимого оказывается под раскрытием.

Нужно сделать эти поля действительно пригодными для работы.

### Требования

Для каждого поля определить:

- разумный видимый размер;
- удобство редактирования;
- отображение большого количества текста;
- поведение при длинном содержимом;
- лимит YouTube, если он применим;
- счётчик символов, если это полезно;
- визуальное состояние приближения к лимиту;
- состояние превышения лимита.

Не нужно просто бесконечно увеличивать высоту страницы.

Нужно найти хороший баланс между:
- количеством одновременно видимого текста;
- компактностью;
- удобством редактирования.

Если существующая система раскрытия всё ещё нужна — использовать её осмысленно, а не как способ спрятать основное рабочее содержимое.

---

# 4. Поля под раскрытием — провести аудит

Сейчас часть данных уже приходит от YouTube, но некоторые данные спрятаны под spoiler/collapsible sections.

Для каждого такого поля определить:

1. Нужно ли оно вообще обычному пользователю?
2. Нужно ли показывать его всегда?
3. Достаточно ли показывать его в раскрываемом блоке?
4. Должно ли оно быть readonly?
5. Должен ли пользователь его редактировать?
6. Если редактировать — какой control наиболее естественен?

Не делать все поля редактируемыми автоматически.

---

# 5. «Техническая информация»

Отдельно проанализировать раздел `Техническая информация`.

Задать вопрос:

> какую реальную пользовательскую ценность этот раздел даёт владельцу YouTube-канала?

Если это в основном:
- внутренние ID;
- технические значения;
- служебные данные;
- информация, полезная разработчику, но не пользователю;

не оставлять такой раздел в основном пользовательском интерфейсе просто потому, что данные существуют в API.

Предпочтительный результат:

- убрать из основного UI;
- либо существенно сократить;
- либо оставить только действительно полезные пользователю данные.

Не создавать новый сложный diagnostics UI без необходимости.

---

# 6. Поля должны быть управляемыми там, где это имеет смысл

Одна из целей Stage 3 — перестать воспринимать полученные от YouTube данные только как текст для отображения.

Для каждого существующего пользовательского поля определить подходящий тип управления.

Примеры:

```text
число
→ +/- или другой компактный numeric control

да/нет
→ checkbox / switch

один вариант
→ radio / segmented control

много вариантов
→ select / dropdown

категория
→ понятный select

длинный текст
→ textarea/editor

список значений
→ соответствующий list/chips control
```

Но это НЕ означает, что каждое поле обязательно должно стать editable.

Для каждого поля сначала определить его назначение.

---

# 7. Video category

Если сейчас категория отображается как числовой ID, это нужно исправить на уровне UI.

Пользователь должен видеть понятное название категории.

Например:

```text
Категория
[ Education ▼ ]
```

а не:

```text
Category ID
27
```

Backend/API может продолжать использовать ID.

UI должен показывать человеку понятное значение.

Если категория пока не должна быть изменяемой из-за отсутствия write-логики — всё равно отображать её человеческим названием.

---

# 8. Playlists — самостоятельный раздел

Это важное изменение структуры, но оно НЕ должно превращаться в глобальный redesign.

Сейчас плейлисты находятся внутри карточки каждого видео и фактически показываются как список плейлистов канала.

Это не соответствует пользовательской модели.

`Playlists` должен стать самостоятельным основным разделом Studio наравне с `Videos`.

Новая модель:

```text
PLAYLISTS

слева                         справа

список плейлистов             содержимое выбранного плейлиста
                              список видео
```

Например:

```text
A1 Deutsch
A2 Deutsch
Grammatik
Wortschatz
...
```

При выборе:

```text
A2 Deutsch

1. Video A
2. Video B
3. Video C
4. Video D
```

Пользователь может выбрать видео из содержимого плейлиста.

При выборе видео должна открываться/использоваться уже существующая карточка видео, а не создаваться вторая независимая карточка.

Цель:

> один Video workspace используется независимо от того, откуда пользователь пришёл к видео.

Источники могут быть:

```text
Videos → Video
Playlists → Playlist → Video
```

Но карточка видео остаётся одна.

---

# 9. Playlist data

Проверить, какие данные о плейлистах уже реально получаются из YouTube и сохраняются/кэшируются.

Не добавлять новую сложную backend-модель без необходимости.

Если существующего API достаточно — использовать его.

Если для полноценного Playlist workspace требуется небольшое API-изменение, сделать минимальное изменение.

Не реализовывать пока полноценное редактирование плейлистов YouTube, если оно не является частью текущего Stage 3.

Stage 3 должен сначала правильно представить структуру.

---

# 10. Channel switcher

Сейчас сверху рядом с логотипом есть переключатель каналов.

Пользователь не уверен, что это правильное место для мгновенной смены активного канала.

Проблема особенно важна для будущего write-mode:

> пользователь может случайно переключить канал и не заметить, что теперь работает с другим каналом.

Не делать автоматический глобальный redesign.

Проанализировать существующий UX и выбрать минимальное решение.

Предпочтительная модель:

- текущий канал явно отображается как контекст Studio;
- смена канала является осознанным действием;
- если канал действительно меняется, пользователь получает явное подтверждение;
- Cabinet остаётся местом управления каналами.

Если после анализа текущего UI верхний switcher можно сохранить без риска — не удалять его просто ради удаления.

---

# 11. Channels и Google Connections

Сейчас пользователь может увидеть возможность добавить/подключить канал в двух местах:

- Connections;
- Channels.

Это выглядит как дублирование.

Нужно разобраться в существующей архитектуре и пользовательском смысле этих разделов.

Основная пользовательская сущность должна быть:

> Channel.

Google connection — технический механизм авторизации/доступа к каналу.

Проверить возможность объединить пользовательский flow так, чтобы:

- канал был главным объектом;
- не было ощущения двух одинаковых способов добавить канал;
- информация о Google account была показана только если она действительно полезна пользователю;
- например, можно показать связь:

```text
Channel
Google account: user@example.com
```

если это помогает понять, откуда берётся доступ.

Но не перегружать пользователя OAuth/service information.

Не удалять backend connection model только ради упрощения UI.

Речь идёт именно о пользовательском представлении и flow.

---

# 12. Local snapshot / YouTube snapshot

Сейчас элементы вроде:

- `Local`;
- `YouTube snapshot`;

и соответствующие кнопки разрешения конфликта могут выглядеть как обычные постоянно доступные действия.

Это неправильно.

Пользователь не должен постоянно видеть кнопки, смысл которых он не понимает.

Новая модель:

```text
обычное состояние
→ никаких конфликтных кнопок

обнаружен конфликт
→ понятное предупреждение

→ показать варианты разрешения
```

Например:

```text
Обнаружены различия между локальными данными и YouTube.

[Использовать данные YouTube]
[Оставить локальные данные]
```

Конкретные названия определить на основании существующей модели данных.

Не реализовывать опасные write-операции только ради демонстрации UI.

Если действие пока не может быть безопасно выполнено — оно должно быть явно обозначено как недоступное/будущее, а не создавать ложное ощущение готовой функции.

---

# 13. Не смешивать snapshot и working state

Существующая архитектура различает данные YouTube и будущие рабочие поля.

Не ломать это разделение.

UI должен постепенно становиться понятным человеку:

```text
что сейчас на YouTube
vs
что пользователь хочет получить
```

Но не создавать сложный diff/merge interface, если для этого ещё нет реальной write-логики.

Stage 3 должен подготовить хороший UX-фундамент для следующего этапа.

---

# 14. Общий аудит Studio UI

После выполнения конкретных пунктов пройти весь Studio сверху вниз.

Проверить:

### Navigation
- понятны ли разделы;
- нет ли дублирования;
- соответствует ли название раздела его содержимому.

### Lists
- понятно ли, что можно выбрать;
- достаточно ли информации для выбора;
- нет ли лишних технических значений.

### Cards
- понятно ли, что редактируется;
- понятно ли, что readonly;
- нет ли чрезмерного количества collapsed sections.

### Controls
- понятен ли тип действия;
- соответствует ли control типу данных.

### Actions
- понятно ли, что произойдёт после нажатия;
- нет ли опасных действий рядом с обычными;
- не показываются ли действия, которые сейчас не нужны.

### States
Проверить:
- loading;
- empty;
- error;
- stale;
- partial;
- selected;
- conflict;
- unavailable.

Не переписывать существующую state machine без необходимости.

---

# 15. Responsive behavior

Сохранять существующую responsive-систему.

Проверить минимум:

- mobile;
- tablet;
- desktop.

Особенно проверить новый Playlist workspace.

Не допускать горизонтального overflow и ситуаций, когда основные controls становятся недоступны.

---

# 16. Browser verification обязательна

После изменений обязательно реально запустить приложение и проверить UI через browser.

Если для проверки нужны оба сервера:

- Next.js;
- FastAPI;

агент должен самостоятельно запустить их.

Не считать проверкой ситуацию, когда frontend просто отвечает HTTP 200.

Нужно реально пройти основные экраны приложения.

Минимальный сценарий:

```text
login/session state
→ Cabinet
→ Studio
→ Videos
→ выбрать видео
→ проверить карточку
→ Playlists
→ выбрать playlist
→ увидеть его videos
→ выбрать video
→ проверить переход к карточке
→ проверить channel context
```

Проверить минимум desktop и mobile viewport.

Если browser automation снова не может открыть приложение:

1. определить причину;
2. проверить процессы/порты;
3. проверить backend;
4. проверить frontend;
5. исправить локальную проблему запуска, если она относится к проекту;
6. повторить проверку.

Не объявлять browser verification `unavailable` после первой неудачной попытки, если проблему запуска можно диагностировать и исправить.

Но не обходить проблему фиктивными данными, если из-за этого нельзя проверить реальное приложение.

Synthetic fixtures допустимы только там, где они действительно необходимы для безопасной проверки UI и не создают ложного подтверждения backend-функциональности.

# 17. Tests

После изменений:

- запускать существующие backend tests;
- запускать frontend tests;
- запускать lint;
- запускать production build;
- запускать `git diff --check`.

Если изменена функциональность, добавить/обновить соответствующие тесты.

Не удалять существующие тесты ради прохождения проверки.

# 18. Не делать в Stage 3

Не делать без отдельного задания:

- глобальный redesign;
- смену визуального стиля;
- новую дизайн-систему;
- переписывание всей навигации;
- видео upload;
- хранение видеофайлов;
- полноценную замену YouTube Studio;
- массовые write-операции YouTube;
- сложный background processing;
- Celery/Redis;
- новые внешние сервисы;
- новые authentication providers;
- Apple login;
- новые крупные backend-сущности только ради UI;
- функции, которые не нужны для описанных пользовательских сценариев.

Особенно важно:

> Не превращать Stage 3 в «давайте сразу сделаем весь SaaS».

---

# 19. Работа с существующими незакоммиченными изменениями

Перед началом проверить `git status`.

Не удалять и не откатывать существующие пользовательские изменения.

Не делать reset/clean.

Если в worktree уже находятся изменения Stage 3 или связанные с текущим handoff изменения — сначала разобраться, что именно уже сделано, и продолжать от фактического состояния.

---

# 20. Commits

Пользователь специально просит:

> НЕ делать commit и НЕ делать push после завершения Stage 3.

Все изменения оставить в рабочем дереве.

Пользователь сначала сам проведёт визуальную проверку.

После визуальной проверки пользователь отдельно решит, когда и что коммитить.

---

# 21. Финальный отчёт

После завершения Stage 3 дать краткий отчёт:

1. Что изменено.
2. Какие пункты Stage 3 закрыты.
3. Какие пункты сознательно не делались.
4. Какие файлы существенно изменены.
5. Какие тесты прошли.
6. Результат browser verification.
7. Какие реальные пользовательские сценарии проверены.
8. Есть ли известные ограничения.
9. Точный `git status`.
10. Подтвердить:
   - commit НЕ делался;
   - push НЕ делался.

Обновить `STATUS.md` по фактическому состоянию.

Не объявлять Stage 3 полностью завершённым, если существенный пункт из этого ТЗ фактически не выполнен.

### Правила экономии агентного лимита

Работай экономно с агентным лимитом.

- Не перечитывай большие файлы и участки репозитория, которые уже были проверены и не изменились.
- Не повторяй аудит, если соответствующая часть проекта уже была проверена в рамках текущей задачи.
- Перед началом каждого нового шага сначала используй уже полученные факты и результаты предыдущих шагов.
- Не запускай команды, которые не нужны для текущей задачи.
- Не выполняй дополнительные исследования "на всякий случай".
- Если для выполнения задачи достаточно точечной проверки нескольких файлов, не сканируй весь репозиторий.
- Сохраняй промежуточные выводы в STATUS.md только тогда, когда это предусмотрено текущим планом работы.
- Приоритет — корректность и безопасность изменений, но без лишнего расходования агентного контекста.

# Definition of Done

Stage 3 считается завершённым, когда:

- существующий интерфейс сохранён как основа;
- Video workspace стал удобнее для реальных объёмов Title/Description/Tags;
- технический шум убран или обоснован;
- поля под раскрытием прошли аудит;
- понятные данные получили подходящие controls там, где это действительно нужно;
- Category отображается человеком понятным значением;
- Playlists стали самостоятельным основным разделом;
- Playlist → Video использует существующую Video card;
