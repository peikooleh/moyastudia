# MoyaStudia — Full Audit & Remediation Plan — 2026-10-07

## Baseline

- Audited branch: `main`.
- Baseline commit: `cd791c321f5d738beecc2ace8b892d66ce788d61` (`Merge security hardening and YouTube write fixes`).
- Remediation branch: `audit-remediation-2026-10-07`.
- The merge commit contains the exact tested source tree from `security-audit`; the last PR CI on that tree passed API pytest and frontend Node tests/lint/build.

## Overall assessment

No P0/critical issue requiring the application to be disabled was found.

The current security boundary is materially stronger than the earlier prototype: authenticated ownership checks are server-side, mutation requests require same-origin validation, Write Mode is server-authoritative for YouTube mutations, refresh tokens and AI API keys are encrypted at rest, upload bodies are bounded, and status/metadata writes preserve unrelated YouTube fields.

The largest remaining risks are reliability/integrity around multi-request YouTube mutations, catalog synchronization strategy, release gates, dependency hygiene, and UI regression risk caused by large coupled frontend files.

## Findings

### P1 — YouTube multi-request writes can end in ambiguous partial state

Affected areas:
- adding multiple videos to a remote playlist;
- full playlist reorder;
- caption insertion after an uncertain network/provider result;
- combined video metadata + visibility save in the frontend.

`add_videos_to_playlist()` performs one `playlistItems.insert` per video and returns only after the loop completes. `reorder_playlist_items()` performs multiple `playlistItems.update` operations. If a later request fails, earlier requests may already have succeeded remotely while the API returns a generic failure. A user retry can therefore duplicate a playlist item or continue from an unknown remote order.

Remediation:
1. classify mutations as idempotent / reconcile-before-retry / non-idempotent;
2. return structured partial-result data for batch operations;
3. reconcile remote playlist membership/order after uncertain outcomes;
4. prevent duplicate membership inserts when the desired membership already exists;
5. add write-operation audit records without storing secrets;
6. add regression tests for failure after the first successful remote mutation.

### P1 — Catalog sync uses the Search API instead of the channel uploads playlist

`fetch_channel()` already retrieves `contentDetails.relatedPlaylists.uploads`, and the catalog sync model already has `uploads_playlist_id`, but `list_videos()` ignores that argument and calls `search.list(forMine=true)` on every page.

Under the current YouTube granular quota model, `search.list` has its own default daily bucket of 100 calls. Google documents the uploads playlist as the canonical list of uploaded videos and demonstrates enumerating it through `playlistItems.list`.

Remediation:
1. obtain/persist the uploads playlist ID;
2. page with `playlistItems.list` at up to 50 items;
3. batch hydrate video details with `videos.list`;
4. keep the current incremental-overlap and reconcile semantics;
5. add migration-compatible fallback for channels whose sync row has no uploads ID;
6. add tests proving no `search.list` is required for normal catalog sync.

Official references:
- https://developers.google.com/youtube/v3/docs/channels
- https://developers.google.com/youtube/v3/docs/playlistItems/list
- https://developers.google.com/youtube/v3/docs/search/list

### P1 — Release protection is incomplete

Observed:
- CI triggers on `pull_request` only;
- `main` is currently unprotected and has no required status checks;
- `npm run check:i18n` is not part of CI;
- there is no dependency/security audit job;
- there is no automated browser/E2E smoke gate for the application shell and critical write flows.

Remediation:
1. run CI on pull requests and pushes to `main`;
2. add i18n parity to CI;
3. add a dependency advisory check suitable for Python and npm;
4. add browser smoke/E2E coverage for anonymous/authenticated shell, Videos, Playlists, Calendar, Statistics, Cabinet and Write Mode gating;
5. configure GitHub branch protection/ruleset for `main` with required checks and no direct push.

### P1 — Known-vulnerable/outdated Python pins need a controlled upgrade

Current pins include:
- `requests==2.32.3`, while the credential-forwarding/netrc issue fixed in 2.32.4 affects that version family;
- `cryptography==44.0.0`, which is within the affected range for CVE-2026-69247, fixed in 50.0.0.

The audited application does not directly use the vulnerable PKCS#7 decrypt APIs; token encryption uses Fernet. No direct application import of `requests` was found in repository code, so the observed advisories are dependency-hygiene findings rather than evidence of an active exploit path in MoyaStudia.

Remediation:
1. update in isolated commits;
2. prefer a currently maintained patch line compatible with Python 3.12 and Google libraries;
3. run the full backend suite and real OAuth smoke after each dependency family update;
4. add automated advisory checks so known vulnerable pins do not remain unnoticed.

### P2 — Statistics refresh is too eager

Opening Statistics for a channel starts catalog sync even when a usable complete catalog already exists. This adds latency and provider traffic on normal navigation.

Remediation:
- introduce freshness semantics (for example last-success age / explicit stale state);
- use cached complete catalog immediately;
- refresh only when stale, explicitly requested, or required for a missing scope;
- preserve a visible manual refresh/reconcile action.

### P2 — Provider calls need one reliability policy

Google/YouTube calls are created in multiple helper functions with no project-level timeout/retry/reconciliation policy. Video metadata/status routes intentionally hold a row lock while the remote write is in flight to serialize writes to the same video; a slow provider request therefore also lengthens the database lock.

Remediation:
- centralize provider execution settings;
- set explicit timeouts;
- retry reads/transient safe operations only;
- never blindly retry unknown-outcome mutations;
- reconcile state before retrying a non-idempotent write;
- keep quota recording isolated from the domain transaction.

### P2 — Frontend architecture has regression-prone coupling

Current large files:
- `apps/web/app/studio.js`: ~2.7k lines;
- `apps/web/app/globals.css`: ~3.6k lines;
- `apps/web/lib/i18n.js`: ~2k lines;
- `apps/api/app/main.py`: ~2.5k lines.

The CSS has many overlapping responsive breakpoints and repeated selectors. This is consistent with the historical visual regressions where a local page change affected neighboring pages.

Remediation must be incremental, not a broad rewrite:
1. extract Videos, Playlists and Calendar by real feature boundary;
2. move feature-specific CSS next to those boundaries or into clearly scoped sections/modules;
3. keep shared design tokens/header/layout primitives centralized;
4. split backend routers/services by domain only as touched by remediation work;
5. keep all changes behavior-preserving unless a finding explicitly requires behavior change.

### P2 — Accessibility and custom-menu behavior need a focused pass

Source-level issues:
- Statistics channel selector declares `aria-haspopup="listbox"` but the popup is a plain `div` of buttons without matching listbox/option semantics or full keyboard behavior;
- Calendar context menu uses menu roles but has no visible roving-focus/escape management in the component;
- Statistics trend bars expose values mainly through mouse `title` text rather than an equivalent screen-reader representation;
- native `window.confirm` is used throughout Studio/Cabinet and is visually inconsistent with the rest of the product.

Remediation:
- either use correct native controls or implement complete keyboard/focus semantics;
- add accessible chart summary/table text;
- standardize destructive/YouTube-write confirmations in one reusable dialog after behavior is covered by tests.

### P2 — Video Save can partially succeed without an explicit partial-success UI

The Videos inspector can publish metadata first and then change visibility. If the metadata update succeeds and the status update fails, the catch path reports an error but does not clearly tell the user that metadata is already live on YouTube.

Remediation:
- model the two remote mutations as explicit steps;
- reload/reconcile after any remote success followed by a later failure;
- show a partial-success message and leave only the failed step staged.

### P2 — Product/API contract for Statistics video scope is enforced only in UI

The Statistics UI offers only available public videos, but the backend analytics endpoint accepts any owned catalog video ID with a YouTube ID.

This is not an authorization vulnerability because ownership is still enforced. It is a product-contract inconsistency.

Remediation:
- decide whether private/unlisted analytics are intentionally supported;
- if public-only is the product rule, enforce it server-side and test it.

### P2 — Production rate limiting is process-local (deployment gate)

The rate limiter is an in-memory fixed-window limiter. It is useful protection for the current single-process shape, but counters reset on restart and are not shared across workers/instances.

Remediation before horizontal/public scale:
- move rate-limit state to a shared backend or edge/gateway;
- keep separate OAuth/provider/write/upload buckets;
- preserve hashed session/OAuth keys and avoid logging raw credentials.

### P2 — CSP is good but can be tightened

Current production headers include CSP, HSTS, frame denial, nosniff, referrer policy and permissions policy. The CSP still permits `'unsafe-inline'` scripts and a broad `connect-src https:`.

Remediation:
- evaluate nonce/hash-based Next.js CSP;
- narrow `connect-src` to the actual API/provider endpoints required by the browser;
- do not weaken the current frame/object restrictions.

### P2 — i18n validation checks parity but not duplicates

The current parity script compares key sets. The audited file currently has 669 unique keys in each of EN/RU/UK and no duplicates, but a duplicate key would be silently collapsed by the Set-based check.

Remediation:
- make the script fail on duplicate keys;
- add it to CI;
- report the actual key count in generated/maintained documentation rather than a stale manual number.

### P3 — Documentation contains stale contradictory state

Examples:
- `STATUS.md` says 664 i18n keys while the current source has 669;
- the historical bottom section still contains a "do not merge" gate that has already been superseded;
- architecture/write-mode documents still mix implemented behavior with old planned stages.

Remediation:
- keep a short current-state section as the source of truth;
- clearly mark/archive historical handoffs;
- update architecture diagrams/contracts as code boundaries change;
- update README/HOWTOSTART/WRITE_MODE_DESIGN/STATUS in the same commits as behavior changes.

## Visual audit scope

A source-level visual/UX audit is complete for the current repository: layout structure, responsive CSS, page coupling, controls, menu semantics, focus-related markup and known lint warnings were reviewed.

A true pixel/runtime visual audit still requires the authenticated application running in a browser with real or representative data. GitHub source inspection cannot validate clipping, scroll behavior, popup placement, loading-state geometry or the agreed desktop/mobile viewport set. Therefore browser QA is an explicit release gate in the remediation plan, not something this document claims as already completed.

Required viewports:
- 1440×900;
- 768×1024;
- 390×844;
- 844×390.

Required pages:
- Videos;
- Playlists;
- Calendar;
- Statistics;
- Cabinet;
- anonymous/onboarding/header states.

## Execution plan

### Phase 0 — Baseline/release gates
- branch from the exact audited `main`;
- update current documentation;
- CI on PR + push to `main`;
- i18n duplicate/parity validation in CI;
- dependency advisory checks;
- define branch protection requirements.

### Phase 1 — Provider integrity
- add operation result/reconciliation model;
- make playlist add/reorder partial outcomes explicit;
- prevent duplicate playlist inserts;
- handle caption unknown-outcome safely;
- add tests for mid-batch/provider failures;
- improve partial-success handling for combined video metadata/status save.

### Phase 2 — Catalog transport
- replace normal `search.list` catalog enumeration with uploads playlist + `playlistItems.list`;
- retain `videos.list` hydration and current snapshot/working semantics;
- reduce Statistics automatic sync to freshness-driven refresh;
- add quota/sync tests.

### Phase 3 — Dependency/security hardening
- controlled Python dependency updates;
- shared/production-ready rate-limit design for deploy phase;
- provider timeouts and retry policy;
- CSP/connect-src tightening where compatible;
- standardized safe provider error codes.

### Phase 4 — UI boundaries and accessibility

Implemented before browser QA:
- corrected Statistics channel-menu semantics and Escape/focus behavior;
- added a screen-reader representation for Statistics trend data while keeping visual bars decorative;
- added Escape paths and accessible naming for Playlist transient dialogs and the Calendar context menu;
- removed Cabinet's hidden per-channel provider profile refresh on ordinary page load.

Deferred deliberately until after the visual stabilization gate:
- studio.js remains a high-coupling file (~2.7k lines); extracting Videos/Playlists/Calendar before the authenticated visual pass would enlarge the regression surface without changing product behavior;
- feature CSS scoping and reusable confirmation-dialog work remain follow-up refactors that should be covered by browser tests first.

### Phase 5 — Automated browser QA
- add browser smoke/E2E coverage;
- exercise Write Mode OFF/ON, metadata/status partial failures, playlist writes and calendar staging;
- run the four required viewport checks;
- capture/compare visual regression evidence for the pages affected by CSS refactoring.

### Phase 6 — Documentation and final gate
- update README, HOWTOSTART, STATUS, MoyaStudia_ARCHITECTURE and WRITE_MODE_DESIGN to the implemented state;
- remove or clearly mark superseded handoff/gate text;
- run backend pytest, frontend tests, i18n, lint, production build, browser QA and security/dependency checks;
- merge only when all required checks are green and the final visual pass is accepted.

## Merge policy for this remediation branch

Do not merge broad batches. Each phase should be split into reviewable commits with tests and documentation updated alongside the code. High-risk YouTube write changes must be completed and tested before UI refactoring. Visual refactoring must not change remote mutation semantics.
